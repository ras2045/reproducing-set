Recall

A chat frontend for Ollama that only trusts an answer once the model has given it consistently, then serves it instantly instead of re-running the model at all.

Why it's not exact-match caching

Most response caches key on exact text. This one embeds every prompt and matches by cosine similarity, and it doesn't trust a match just because it's similar — a pattern only becomes eligible to short-circuit a live call after the model has answered it (or something close to it) the same way three times running. A minimum-consistency slider in the UI controls how strict that bar is. A prompt that never settles into a consistent answer within five attempts is abandoned and always goes to the model live.

1Prompt comes in → checked against learned patterns by embedding similarity.
2No trusted match → goes to the model for real; the pair is recorded in the background.
3Consistent for 3 attempts in a row → the pattern activates and becomes eligible.
4Next similar prompt, above the slider's threshold → instant answer, no model call.

Tested, not assumed

A real question was sent through a real 8B model: 28.5 seconds, correct answer. Fed through the learning loop three times (100% measured consistency), it activated. The same question then returned in 0.076 seconds — the identical answer, ~375× faster. Killed the server process and restarted it: the learned pattern and the threshold setting were both still there, loaded straight from disk.

What got left out, on purpose

This is a cleaned-up extraction from an earlier research prototype. Cut before shipping:

  • A custom compression codec for the cache's own storage
    its headline ratio was measured on a tiny, repetitive sample and didn't hold up on an independent test — plain gzip'd JSON instead
  • A "ring" content-routing signal
    already proven, in this same research, to be uncorrelated with prompt content
  • Framework-specific system prompts, RAG hookup, an arXiv lookup proxy
    none of it general-purpose; none of it shipped
